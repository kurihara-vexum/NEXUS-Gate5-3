# Gate5 提出物

PC貸出処理を、空のリポジトリから実装したWebアプリです。洗い出し表のうち、データ破損・不整合につながる優先度「高」の項目と、提出写真で必須の過去日エラーだけを実装対象にしました。

## 1. 起動手順

必要なものは Python 3.9 以上だけです。外部パッケージは使用していません。

```bash
git clone https://github.com/kurihara-vexum/NEXUS-Gate5-3.git
cd NEXUS-Gate5-3
python3 app.py
```

ブラウザで <http://127.0.0.1:3000> を開きます。テストは次のコマンドで実行します。

```bash
python3 -m unittest -v
```

画面右上の「初期状態に戻す」を押すと、撮影用の初期データに戻せます。

### 必須写真の撮影手順

1. 正常時の貸出完了: `PC-0001`、明日以降の日付、利用目的を入力し、確認画面で確定する。
2. エラー① 状態チェック: 初期状態に戻し、貸出中の `PC-0002` を選び、確認画面で確定する。
3. エラー② 入力値チェック: 初期状態に戻し、`PC-0001` の返却予定日に過去日を指定して確定する。
4. エラー③ 任意: 初期状態に戻し、利用目的に `動作確認 (^_^)` と入力して確定する。顔文字エラーを撮影できる。

## 3. 実装した項目 / 実装しなかった項目

| No | 項目 | 優先度 | 実装 | 理由 |
| -- | -- | --- | -- | -- |
| 1 | 選択した端末が既に貸出中 | 高 | ○ | 確定時に端末状態と未返却レコードを同一トランザクション内で再確認するため |
| 2 | 休職・退職した社員が貸出申請 | 高 | ○ | サーバーで認証済み社員の在職状態を確認してから登録するため |
| 3 | 貸出可能端末が存在しない | 低 | × | データ不整合に直結しないため今回の対象外 |
| 4 | 貸出台数の上限超過 | 中 | × | データ不整合に直結しないため今回の対象外  |
| 5 | 同じ申請を2回送信 | 中 | × | 同上。なお同じ端末の二重貸出はNo.1とDB制約で防止 |
| 6 | 2人が同時に同じ端末を選ぶ | 高 | ○ | `BEGIN IMMEDIATE`で直列化し、DBの部分一意インデックスでも未返却貸出を1件に制限するため |
| 8 | 返却予定日が過去 | 中 | ○ | 必須写真の対象。画面だけでなくサーバーでも明日より前の日付を拒否するため |
| 9 | 返却予定日が先すぎる | 中 | × |8に似ているため|
| 10 | 存在しない日付 | 中 | × | 8に似ているため|
| 11 | 返却予定日が当日 | 中 | × | No.8の「明日以降」判定には含まれるが、独立項目としては実装対象外 |
| 12 | 返却予定日が空欄 | 中 | × | 通常入力に必要なHTML必須指定のみ。独立した例外仕様は対象外 |
| 13 | 利用目的が空欄 | 中 | × | 通常入力に必要なHTML必須指定のみ。独立した例外仕様は対象外 |
| 14 | 利用目的が100文字超過 | 中 | × | HTMLの入力上限のみ。独立した例外仕様は対象外 |
| 15 | 利用目的に顔文字・絵文字 | 中 | ○ | 顔文字パターンとUnicodeの絵文字範囲をサーバーで検知し、保存前に拒否するため |
| 16 | 借りていない端末を返却 | 中 | × | 通常の返却成立条件だけを確認し、独立した例外画面は対象外 |
| 17 | 延滞中ユーザーが新規貸出 | 中 | × | データ不整合に直結しないため今回の対象外  |
| 18 | 複数テーブル更新の途中で失敗 | 高 | ○ | 貸出・返却とも2テーブルの更新を1トランザクションにし、途中失敗時は全件ロールバックするため |
| 19 | DB接続断・タイムアウト | 高 | ○ | DB例外時に成功扱いせず、安全なエラーを表示する。未確定トランザクションはロールバックされるため |
| 20 | 他人のIDを指定して実行 | 高 | ○ | 利用者IDをフォーム項目にせず、サーバー側の認証済みIDだけを使用するため |

## 5. 振り返り

### 5-1. 自分の洗い出しで、項目が 0 件だった観点カテゴリはどれですか。

ありません。8カテゴリすべてで最低1件を洗い出しました。

### 5-2. 「言われれば当たり前」だったのに気づけなかった項目を 3 つ挙げ、なぜ自力で気づけなかったかを書いてください。

1. 画面で貸出可能に見えても、確定までの間に別の人が先に借りる可能性があることです。一人で順番に操作する場面だけを想像し、同時実行を時間軸で考えられていませんでした。
2. 貸出記録の追加と端末状態の更新の片方だけ成功すると、履歴と一覧が食い違うことです。画面遷移を中心に考え、複数テーブルを一つの業務処理として見られていませんでした。
3. 画面に利用者IDの入力欄がなくても、リクエストを改変して他人のIDを送れることです。通常の画面操作だけを想定し、サーバー側で何を信用してよいかを考えられていませんでした。

### 5-3. Gate1 の振り返りで書いた「確認しに行くこと」リストと比べて、増えた観点は何ですか。

Gate1では、ステータスや権限、画面表示など、主に通常操作に必要な仕様を確認する観点が中心でした。Gate5ではそれに加えて、2人が同じ端末を同時に借りようとした場合の競合、ボタンの連打や再送信による二重登録、複数テーブルの更新途中で失敗した場合のロールバックなど、データの整合性を守る観点が増えました。また、過去日や未入力などの入力値、処理の順序、DB接続断などの障害、URLの直接操作や他人のIDへの書き換えといった不正操作についても、事前に確認する必要があると気づきました。
